WHAT THIS DOCUMENT IS
--------------------------------------------------------------------------------

You are going to build a model that answers questions like:

    STATE:      "I was charged twice for order 4411. Please refund one charge."
    QUESTION:   Which team should handle this?
    OPTIONS:    1. billing  2. shipping  3. technical support
    ANSWER:     billing, with probabilities {billing: 0.91, shipping: 0.06, ...}

...across text, images, audio and video, in a single forward pass, on a laptop.

The model you are copying is `akhilaaa3/Jev-Omni`: a 12-billion-parameter
decision classifier built on Google's Gemma 4 12B. It is genuinely good. It is
also expensive -- roughly 24 GB of weights in bf16, a CUDA GPU required, and a
reported 83 ms per text decision on an H200, which is a datacenter accelerator
that costs about $2-3/hour to rent.

You want the same *interface* on something like 1/34th of the parameters, that
runs on a Raspberry Pi.

That is what this guide is for.

================================================================================
PART 0 -- THE THIRTY-SECOND VERSION
================================================================================

If you read nothing else, read this.

WHAT JEV-OMNI IS
    A language model with its text-generation ability replaced by a classifier
    head. You give it a situation and a question with options; it gives back a
    probability for every option. It never writes a sentence. That is the entire
    trick, and it is worth ~99% of the cost saving.

WHAT WE ARE CHANGING
    Backbone:   Gemma 4 12B  ->  Liquid AI LFM2.5-350M   (12B -> 350M, ~34x)
    Head:       Linear(3840, 256)  ->  Linear(1024, 256)
    Training:   2.1 billion trainable LoRA params, 4 GPUs  ->  ~6 million, 1 GPU
    Latency:    83 ms on H200  ->  tens of ms on a laptop CPU
    Cost:       needs a datacenter GPU  ->  runs on a Raspberry Pi 5

WHAT WE ARE NOT CHANGING
    The idea. The head is still Linear(hidden, 256). The prompt still numbers the
    options. The output is still a softmax over 256 slots. Everything the original
    author got right, we keep.

THE HEAD IS ALMOST FREE
    LFM2.5-350M has 354,483,968 parameters. Our decision head adds 262,400.
    That is 0.074% of the network. You could attach this head to a 10B model and
    it would still be invisible in the parameter count. This is why "make it
    smaller" is not a desperate optimisation -- it is mostly about which
    pretrained backbone you start from.

THE ONE THING THAT MATTERS MOST
    A decision model is not a chatbot that happens to be small. It is a
    classifier with a language model's knowledge. Everything else -- the prompt,
    the options, the temperature -- is detail compared to the base checkpoint you
    fine-tune and the calibration you fit afterwards.

================================================================================
PART 1 -- VOCABULARY, BECAUSE THE TERMS WILL OTHERWISE STOP YOU
================================================================================

1.1 TOKEN
-------
A token is a chunk of text. Not a word -- a *chunk*. The most common words are
one token. Rare words get split into pieces. "Unbelievably" might be 3 tokens.

Why it matters: models read and write tokens, not letters. Every cost formula
you will meet is denominated in tokens. A 2,000-token document is about 1,500
words of English prose.

LFM2.5-350M has a vocabulary of 65,536 tokens. That means every piece of text
becomes a list of integers in the range 0-65535.

1.2 TOKENIZER
------------
The component that turns text into tokens and back. It is a fixed, learned
lookup table plus some rules about splitting. It is NEVER trained. It is part of
the model checkpoint.

    tokenizer.encode("hello world")  ->  [15339, 1917]     (2 tokens)
    tokenizer.decode([15339, 1917]) ->  "hello world"

Pin your tokenizer with your model. If you upgrade the tokenizer, every number
you have measured is now wrong.

1.3 EMBEDDING / HIDDEN STATE / HIDDEN SIZE
-----------------------------------------
Neural networks turn tokens into vectors of numbers. A vector of 1,024 numbers
is a "hidden state" of width 1,024.

`hidden_size` is the width of that vector at every layer.

    LFM2.5-350M    hidden_size = 1024
    LFM2.5-2.6B    hidden_size = 2048
    Gemma 4 12B    hidden_size = 3840

This number is the single most important one for our purposes, because the size
of the decision head is exactly `hidden_size * 256 + 256`.

1.4 LAYER
---------
One transformation of the vector. A model stacks many of them. LFM2.5-350M has
16. Gemma 4 12B has 48.

Not all layers compute the same thing. LFM2.5-350M's 16 layers are:

    conv, conv, full_attention, conv, conv, full_attention, conv, conv,
    full_attention, conv, full_attention, conv, full_attention, conv,
    full_attention, conv
             ^^^^^^^^^^^^^  6 attention layers
    ^^^^^^^^^^^^^^^^^  10 short-convolution layers

That is the "hybrid" architecture. The conv layers are cheap local pattern
detectors. The attention layers let distant parts of the input talk to each
other. Liquid AI found this mix by running an architecture search against real
edge hardware latency, rather than by guessing.

1.5 FORWARD PASS
---------------
One run of the input through all the layers. This is what "inference" means.

A language model runs a forward pass once per generated token -- a 100-token
answer is 100 forward passes. A decision model runs the forward pass **once**,
and that one pass produces the whole answer. This is where the speed comes from.

1.6 LOGIT
---------
A raw, unnormalised score. Higher means "more likely".

    logits = [2.1, -0.3, 0.7]        # not probabilities, do not sum to 1

1.7 SOFTMAX
-----------
Turns logits into probabilities that sum to 1.

    p_i = exp(z_i) / sum_j exp(z_j)

Given logits [2.1, -0.3, 0.7] you get roughly [0.76, 0.07, 0.19].

1.8 LOGIT / LOG-LIKELIHOOD
-------------------------
The log of a probability, before it is turned back into a probability. A
language model's native output is logits over its whole vocabulary -- 65,536
numbers for LFM2.5-350M. When someone says "the model scored option A", they
usually mean "the log-likelihood of the tokens of option A was highest".

1.8 LOGPROB
-----------
The log-probability the model assigned to a token it actually produced. This is
what you get from an LLM API. It is a *generated* number: the model chose to
write those digits. It is not a statement about how confident the model was.

1.10 THE CENTRAL TRAP
--------------------
This is the single most important idea in the whole guide, and it is the reason
decision models exist at all.

    An LLM can WRITE the text "91%".
    That does not mean there is a 91% chance it is right.

The model's log-probability of emitting the characters "9", "1", "%" says how
surprising that *string* was. It is a statement about text, not about truth. A
model that is systematically overconfident will cheerfully write "95% confident"
and be wrong half the time, and the probability it assigns to its own digits will
agree with that claim.

A decision model fixes this by never generating the confidence at all. It reads
the number out of an internal representation and softmaxes it. You cannot
generate a probability you did not compute, and there is no "as an AI language
model" refusal path, because there is no generation.

1.11 CALIBRATION
----------------
A model is *calibrated* when, when it says 80% confident, it is right about 80%
of the time.

Two models can both be 85% accurate. Model A is confident when right and unsure
when wrong. Model B is 95% confident every single time. Same accuracy, wildly
different usefulness -- only A can be used to route work, escalate cases, or set
a threshold.

Calibration is not accuracy. You need both, and you must measure them separately.

1.12 ECE (EXPECTED CALIBRATION ERROR)
------------------------------------
The standard summary number. Split predictions into buckets by confidence; in
each bucket compare confidence to actual accuracy; average the gaps, weighted by
bucket size.

    ECE = sum over buckets of (share of predictions in bucket) * |confidence - accuracy|

Lower is better. Zero is perfect.

CAVEAT, and it is a real one: ECE depends on how many buckets you use and where
you put the edges. DecisionBench reports ECE over 10 equal-width bins in its
table and draws its chart with 5. Those two numbers are NOT comparable. Always
check the binning before comparing two ECE figures.

1.13 BRIER SCORE
----------------
Mean squared error between your predicted distribution and the true one-hot
answer, normalised by the number of options. Lower is better.

Some people argue Brier is better than ECE for this application, and the
`typed-decisions` benchmark makes a strong case: a model that always predicts the
base rate is *perfectly calibrated by construction* (it is never surprised) yet
completely useless. Reporting ECE alone lets that model look good. Report both.

1.14 KL DIVERGENCE
-----------------
How far your distribution is from a reference distribution. `typed-decisions`
reports it as the primary distribution-quality metric, and it is the metric that
moved most when they switched a classifier to soft targets: KL fell by a third.

1.15 LoRA (LOW-RANK ADAPTATION)
-------------------------------
Instead of retraining all 354M parameters, you add a small trainable "sidecar" of
maybe 6M parameters and freeze the rest.

The intuition: the update to a big weight matrix usually has low rank -- you can
express it as a product of two small matrices. So you train only those.

    W' = W + (alpha/r) * B * A

where W is frozen (354M params), A is r x hidden and B is hidden x r are trained.

r=16 on a 1024-wide model gives ~6M trainable parameters -- 1.7% of the model.

Why this matters here: you can train the whole thing on one consumer GPU in
minutes, and you can throw away the adapter and keep the original model.

1.16 QLoRA
----------
LoRA where the frozen base is also quantised to 4 bits during training. Uses
roughly the same memory as training the adapter alone. Matters when your GPU is
small. Not needed for a 350M model on a 24 GB card, but useful on a 12 GB one.

1.17 bf16 / fp32 / int8 / int4
-----------------------------
How many bits per number.

    fp32   32 bits   full precision, baseline
    bf16   16 bits   what these models ship in. ~3 significant decimal digits.
                     Range like fp32, so no overflow. The default.
    int8    8 bits   half the memory, tiny quality loss
    int4    4 bits   quarter the memory, small quality loss

bf16 has a subtlety that will bite you: it can represent 1.0 and 1.0078 but
nothing between. When you compute probabilities in bf16 you get ~3 decimal
digits. That is why our head is fp32 even when the backbone is bf16.

1.18 TEMPERATURE
----------------
A single number you divide logits by before the softmax.

    p = softmax(z / T)

T < 1 sharpens (more confident). T > 1 softens (less confident).

Crucially, temperature CANNOT change which option wins -- softmax is monotonic,
so the argmax is invariant. Temperature only reshapes the distribution around
the winner. That makes it a safe knob to fit after training without changing any
answers.

1.19 CONVOLUTION vs ATTENTION
-----------------------------
Convolution looks at a fixed small window of neighbouring positions. Cheap,
local, fixed receptive field.

Attention lets every position look at every other position, weighted by learned
relevance. Expensive, global.

LFM2.5 uses mostly convolution with some attention. That is why it is fast on
CPUs. Gemma 4 12B uses a 5:1 mix of sliding-window and full attention.

1.20 KV CACHE
-------------
When a transformer processes a prompt, each layer stores the "key" and "value"
vectors it computed, so it does not recompute them. This is the cache.

LFM2.5 also has a *convolution* cache: the last 3 positions' worth of convolution
state (`conv_L_cache: 3`). If you branch a batch -- process several candidate
answers in parallel -- you must copy BOTH caches. Copying only the attention KV
and forgetting the conv state produces a model that is subtly, silently wrong.
The `rlcd` project documented exactly this bug and its fix.

1.21 JSON SCHEMA
----------------
A machine-readable description of a data shape. We use it to describe the
options a question may be answered with.

    {
      "type": "object",
      "properties": {
        "team": {
          "type": "string",
          "description": "Which team should handle this?",
          "enum": ["billing", "shipping", "technical"]
        },
        "urgent": {
          "type": "boolean",
          "description": "True only if immediate action is needed"
        }
      },
      "required": ["team", "urgent"],
      "additionalProperties": false
    }

1.22 TYPED DECISIONS: noul, choice, score
------------------------------------------
The three question types this whole ecosystem converged on. They trace back to
TypeSafe AI's "System One" primitives.

    noul    -- a yes/no statement. Answer: P(true), one number.
    choice  -- one of N named options. Answer: a distribution over options.
    score   -- an ordered rubric ("calm" < "frustrated" < "angry").
               Answer: a distribution over levels PLUS the expected level, which
               can fall between two levels. Expected 1.4 means "between
               Frustrated and Very angry".

Treating these three types explicitly, rather than as free text, is most of what
makes these systems usable: your code gets a guaranteed type.

2.2 THE HEAD -- VERBATIM
------------------------
From `jev_omni.py`, unedited:

    class _Head256(torch.nn.Module):
        """Decision head: normalise the last hidden state, one logit per option slot."""
        def __init__(self, hidden):
            super().__init__()
            self.register_buffer("mu", torch.zeros(1, hidden))
            self.register_buffer("sd", torch.ones(1, hidden))
            self.linear = torch.nn.Linear(hidden, 256, dtype=torch.float32)

        def forward(self, features, counts):
            z = self.linear((features.float() - self.mu) / self.sd)
            return z.masked_fill(torch.arange(256, device=z.device)[None] >= counts[:, None], -1e30)

That is the whole model-specific part. Four things are happening:

(a) TAKE THE LAST HIDDEN STATE.
    A forward hook on the text backbone captures
    `out.last_hidden_state[:, -1].float()`. The final position, because that is
    where the model would have predicted the answer.

(b) STANDARDISE IT. `(features - mu) / sd`, with mu and sd stored as *buffers*,
    not parameters -- fixed statistics, never trained. This keeps the head's
    input well-scaled regardless of what the backbone is doing.

(c) PROJECT TO 256 SLOTS. `Linear(3840, 256)`. These are NOT vocabulary tokens.
    They are 256 *positional option slots*: slot 0 means "option 1", slot 1 means
    "option 2", and so on.

(d) MASK AND SOFTMAX. Slots at or beyond the real option count get -1e30, i.e.
    probability 0. The real slots get softmaxed.

Parameter count: 3840*256 + 256 = 983,456. Against an 11,959,730,224-parameter
model, that is 0.008%.

2.3 WHY SLOT LOGITS, NOT TOKEN LOGITS
-------------------------------------
This is the design decision that makes one checkpoint generalise.

If the head scored the *text* of each option, then "billing" and "shipping" would
need to be known vocabulary, and an unseen label would be unscoreable.

Because it scores *positions in a list*, the same 256 weights handle any
question with any 2-256 options. A model fine-tuned on support tickets can answer
a question about satellite imagery it has never seen, because the head does not
care what the words mean.

The whole method rests on the prompt putting the options in a known order:

    {state}

    ---

    QUESTION: {question}

    OPTIONS:
    1. billing
    2. shipping
    3. technical support

    Reply with only the number of the correct option (1-3).
    Output a single number and nothing else.

The prompt's numbering and the head's slot indexing are two halves of one
contract. Change the renderer and you must retrain.

-----------------------------------

Note what this says. 24,000 examples. One epoch. Rank-512 LoRA. lr 1e-5. A linear

Whatever produced that adapter did so with serious hardware.

350M model. That is 1.7%. We measured this; it is printed by the trainer.

2.6 WHAT IT IS NOT
------------------
Jev-Omni is *not* affiliated with TypeSafe AI. Its own card says so, and says
nothing was trained on Jev output.

TypeSafe AI's "Jev" is a closed, hosted product at $0.042 per million input
tokens. It has no published weights, no published training method, and no paper.
An independent reverse-engineering effort (`archerhume.com`, 17 Sep 2026, based
on 10,000 API calls) concluded the design is "a causal transformer repurposed for
decisions: shared-state encoding, isolated question branches, and direct
probability readouts". The parts it could confirm -- parallel probabilities,
state reuse across questions, question isolation, option interaction before
choosing -- are exactly the parts Jev-Omni implements. The backbone question it
could not answer.

So: Jev-Omni is an independent reimplementation of a *design pattern*, and the
pattern is what you can legitimately copy.

PART 3 -- THE LIQUID AI LFM2.5 FAMILY

3.1 WHAT LFM2 IS
---------------
From the LFM2 technical report (arXiv 2511.23404, 28 Nov 2025):

    "Using hardware-in-the-loop architecture search under edge latency and memory
     constraints, we obtain a compact hybrid backbone that combines gated short
     convolutions with a small number of grouped query attention blocks, delivering
     up to 2x faster prefill and decode on CPUs compared to similarly sized
     models."

Three things in that sentence matter:

- *Hardware-in-the-loop search*. The architecture was chosen by measuring latency
  and memory on real devices, not by a proxy loss.
- *Gated short convolutions*. Most layers are cheap local filters.
- *Grouped-query attention*. A small number of expensive global layers.

-------------------

PART 4 -- THE EXISTING PRIOR ART, AND WHAT IT TAUGHT US
================================================================================

Before designing anything, we read what other people built. There are dozens.
The most instructive:

4.1 notnotsamuel/LFM2.5-350M-RLCD   <- the closest thing to our goal
--------------------------------------------------------------------------
This is almost certainly what you meant by "RCLDs".

Inference-only. The base weights are byte-identical to LiquidAI/LFM2.5-350M at
revision 9e6c6ccf47cd318696e137d381a7ded8fe4df09f. No training at all.

Its method: prefill the context once, deep-copy the hybrid cache (attention KV
*and* the short-convolution state), branch the cache, score every JSON-Schema
candidate value in one batch, sum the log-softmax over each candidate's full
token sequence, take the argmax per field, assemble the JSON in Python.

Its own measured results, 28 boolean fields, FP16:

    M2 Max     393.20 ms constrained vs 3326.95 ms AR   =  8.46x
    L40S        54.12 ms vs 3404.48 ms                   = 62.91x
    H100        43.76 ms vs 2586.97 ms                   = 59.12x
    field accuracy 60.7% / 64.3% / 60.7% vs 53.6% autoregressive

And the honest caveats, which we quote because they matter more than the speedup:

  - "Valid JSON does not mean correct answers: neither method produced a fully
     correct 28-field object."
  - On its 12-case diagnostic suite the constrained method was *faster* but
     *less accurate*: 77.8% vs 80.6% field accuracy.
  - With 255 candidate options on a Mac, constrained inference was 3.23x SLOWER.
  - "They are not calibrated confidence. No calibration evaluation was performed
     and no normalized probability API is exposed."
  - It explicitly does NOT reproduce TypeSafe's training method.

THE KEY LESSON: constraining the decoder gives you *structure* for free, but it
gives you neither accuracy nor calibration. And it does nothing to shrink the
model. We want the head approach AND a smaller backbone, not this.

4.2 akhilaaa3/Jev-Omni
----------------------
The head design we are copying. 12B. 87.57% on DecisionBench Medium, ECE 0.0400.

4.3 jaredpalmer/kev   (0.8B / 4B / 9B / 27B, Apache-2.0)
---------------------------------------------------------
The most carefully documented open family. Key design: a **pointer head** that
scores each option's own `</opt>` hidden state against the question's `<decide>`
hidden state, rather than scoring fixed slots. Options are labelled with single
tokens A, B, C...

Their recipe: LoRA r=16 alpha=32, two epochs, lr 1e-4, ~20 minutes on one H100
for the 0.8B. They ship a fitted temperature per checkpoint.

Their honesty about scale, which we quote directly:

    "It is still a sub-1B model. On the development splits it trails Jev
     everywhere it can be compared: documents 0.842 vs 0.868, hard-v1 0.594 vs
     0.777, devtools-v1 0.602 vs 0.713, out of domain 0.648 vs 0.857."

and:

    "Out of domain it is a sub-1B model. Knowledge (MMLU 0.41) and paraphrase
     (PAWS 0.59) are near the untrained base."

and:

    "Out of domain it is still a sub-1B model: use Kev-4B for accuracy; use this
     one where memory rules the 4B out, and measure on your own data."

and the single most useful sentence in this whole guide:

    "Probabilities are usable in-domain; treat them as advisory elsewhere."

Their 0.8B card also documents fifteen registered training rounds before the
shipped one, and that stacking a second delta on top of a first one *eroded* the
first ("the second delta eroded the first: seed 1's documents lower bound was
-2.03 pp against a -2 pp floor"). Stacking LoRA deltas is not free.

4.4 frontier-infra/jebadiah (4B / 9B, Apache-2.0)
--------------------------------------------------
Their approach differs: option labels are single tokens, and the answer is the
distribution over those label tokens at the last prompt position, read in fp32
from the last hidden state, then temperature-scaled per type.

They ship three temperatures: choice 1.12, noul 1.33, score 1.20.

The finding we care most about is about *how* to fit that temperature:

    "The `hard` fit minimises NLL against the argmax label and sharpens
     (T 0.68 / 0.96 / 0.83). The `train` fit minimises NLL against the training
     target, the soft or ordinal distribution the model was taught, and softens
     (T 1.12 / 1.33 / 1.20). v2 applies `train` ... because the ordinal target is
     what makes rubric probabilities honest, and the `hard` fit is exactly the
     sharpening that made v0's HelpSteer2 calibration worse."

Fitting temperature against the soft target you trained on is not the same as
fitting it against the argmax. We follow the `train` fit, and our
`fit_temperature` documents the choice.

4.5 getainode/jebadiah's own negative results
---------------------------------------------
Their experiment log is the most valuable single document in this field. Things
that did NOT work:

  - A 14,714-question synthetic pool authored by their own teachers made the 9B
    *worse*.
  - A fifth of synthetic choice questions helped a little.
  - Re-targeting synthetic data with a better teacher did not move the headline.
  - Public human yes/no data did not lift their human yes/no eval sets.
  - Two epochs were worse than one.

What DID work:

  - Adding human-rated score data and an ordinal target: HelpSteer2 Decision
    Score went from -21.4 to +11.9 and calibration error from 0.39 to 0.045.
    "The model became honest about not knowing helpfulness rather than better at
    judging it."
  - Switching the base checkpoint from Base to the chat checkpoint, with
    thinking off: worth 2.15 headline points on the 4B, more than any data change
    they made.

Read that last one twice. On the 4B, the single biggest win was the starting
checkpoint, not the data. That is why our default is the instruction-tuned
`LiquidAI/LFM2.5-350M`, not `-350M-Base`.

4.6 logan-markewich/jeff (400M, MIT)
------------------------------------
A different architecture entirely: GLiFormer, a bidirectional encoder, with a
temperature of 3.2 (i.e. substantially overconfident out of the box, corrected by
a large softening factor).

Its JevBench v1.2.2 score of 66.9 ranked #9, but on Intelligence it was #14 of 18.
Its own card: "Cheaper to self-host, but less accurate than jev on reasoning-heavy
tasks."

That is the honest shape of the small-model tradeoff, stated plainly by someone
who built one.

4.7 What converged and what did not
-----------------------------------
CONVERGED (independent implementations agree):
  - A small trained head, not constrained decoding.
  - A pretrained causal backbone, fine-tuned, not trained from scratch.
  - LoRA rather than full fine-tuning.
  - A fitted temperature, shipped with the model.
  - Per-question-type temperatures rather than one global value.
  - Reporting Brier/KL alongside ECE.
  - Explicitly labelling probability as a routing signal, not a truth claim.

DIVERGED (no consensus):
  - Slot logits (Jev-Omni) vs pointer scoring (Kev) vs label-token logits
    (Jebadiah). All three work. Slot logits are simplest and cheapest; we use them.
  - Causal decoder vs bidirectional encoder (jeff, LFM2.5-Encoder). Encoders are
    faster; decoders carry more pretrained knowledge. We use a decoder.
  - Whether questions should be isolated. Kev runs one row per question on hybrid
    DeltaNet bases because those layers ignore attention masks. We run one
    forward pass per question too, and say so.
  - Whether to use soft targets. Jebadiah says yes for rubrics; a benchmark says
    it cut KL by a third; Jebadiah also says a big synthetic soft-label pool made
    things worse. Both can be true: soft targets help, bad soft targets hurt.

================================================================================
PART 5 -- WHAT "RCLD" ACTUALLY MEANS (you asked; it is two different things)
================================================================================

There are two distinct things called RCLD/RLCD in this ecosystem. Both matter to
you. Confusing them is the single most likely reason a beginner mis-builds this.

5.1 RLCD -- REINFORCEMENT LEARNING FOR CALIBRATED DECISIONS
-----------------------------------------------------------
RLCD is TypeSafe AI's own term, from their launch announcement
(typesafe.ai/blog/introducing-system-one-models-and-jev, Diogo Almeida). They compare
three post-training approaches:

    RLHF   Reinforcement Learning from Human Feedback     -- human preference
    RLVR   Reinforcement Learning with Verifiable Rewards -- checkable outcomes
    RLCD   Reinforcement Learning for Calibrated Decisions

Their argument for a third one is worth reading in full, because it is the clearest
statement of why this class of model exists:

    "an output can be compelling to a person without being reliable enough for
     unattended automation. Human preference and machine trustworthiness are
     different optimization targets."

They claim RLHF causes **mode dropping** -- favouring one style while reducing the
probability of other possible outputs -- as "a milder version of GAN mode collapse."

CRITICAL CAVEAT: their announcement does NOT publish the RLCD objective, the data
sources, or the architecture. Their own FAQ headings -- "Why was a new training
algorithm needed?" and "Where does our training data come from?" -- have no answers
on the page. So while the acronym is theirs and the concept is theirs, the method
is not reproducible from public sources.

Other projects have adopted the name for closely related work. Laya
(github.com/NandhaKishorM/laya, Apache-2.0) says it is "trained with reinforcement
learning against strictly proper scoring rules (RLCD)", which is the formal
version of the idea.

This is the important one, because it is the *theoretical* justification for the
entire design.

A scoring rule turns a prediction plus an outcome into a loss. Most of them are
"proper": reporting your true belief minimises your expected loss. A small number
are **strictly proper**: ONLY reporting your true belief minimises it. A model
trained against a strictly proper rule has no way to reduce its loss except by
telling the truth, because any deviation from the truth costs it.

This is exactly the property a decision model needs. It is why the probabilities
are trustworthy enough to threshold on, and it is why "I asked for 80% confident
and the model said 80%" means something.

THE PRACTICAL GOOD NEWS: **you are already doing this.** Cross-entropy
(logarithmic loss) over the option distribution is a strictly proper scoring
rule. Our trainer's loss is literally

    loss = - sum_k  target_k * log_softmax(logits)_k

That is the strictly proper rule, applied to a distribution whose support is
exactly the declared option list. So the SFT recipe in this guide is, in
substance, a strictly-proper-scoring-rule objective. You do not need a
reinforcement-learning loop to get the main benefit.

5.1a THE ONE FREE EXPERIMENT: TRAIN CE ALONGSIDE RLCD
--------------------------------------------------------
The paragraph above argues CE already gives you the main benefit. **The strongest
open system in the field argues the same thing, empirically**, and you should test it
rather than take either of our word for it.

kyr0, who built the best-performing open system on the largest cross-model
benchmark (76.46% against Jev's 88.08% on 22,001 decisions):

    "btw. just one bit on that. RLCD is overrated guys! Use CE as the primary
     loss with an eye on Brier+NLL; it's cheaper and more effective!"

Treat this as ONE SOURCE with a competing system and a commercial interest in
it. It does not overturn anything above. But notice what he is NOT saying: he
is not saying calibration is unimportant. He is saying **CE gets you there
more cheaply** -- which is exactly consistent with our own measurement that
the calibration gap is a FITTING problem (fitted T 3.300 -> 1.050), not a
training-objective problem.

PRACTICAL CONSEQUENCE: this is the cheapest high-value experiment available
to you. Same LoRA arm, same seed, same split, CE as the primary loss, Brier
and NLL reported as metrics instead of as the objective. One extra training
run. If CE matches RLCD, you have removed a dependency on a method that is
**not published** -- TypeSafe never released the RLCD objective (see the
critical caveat above), so training with it is training against folklore.

That is the real argument for the CE arm, and it is stronger than the
performance claim: **a method you cannot reproduce is a liability.**

Where RL proper training *would* add value: the decision to which option a
*human* would pick is not the decision to which option the world is true, and
those differ exactly where the model is useful (routing, escalation, triage). You
can fine-tune against the *task's* reward with a proper rule -- this-that-model-1.0
does precisely that, adapting from decider-2b with "a strictly proper scoring
rule" and reporting that the whole adaptation is a single scalar:

    theta(lambda) = theta_0 + lambda * Delta

with theta(0) bit-exact the prior checkpoint. That is a clean rollback story:
"rollback is a configuration change rather than a restore." Steal that idea.

5.2 LFM2.5-350M-RLCD -- THE INFERENCE-ONLY EXPERIMENT
----------------------------------------------------
`notnotsamuel/LFM2.5-350M-RLCD` is a *different* thing that happens to share the
name. It is inference-only, changes no weights, and its own README says:

    "**Inference only: no training or fine-tuning, and no reproduction of
     TypeSafe.ai's proprietary Jev training method.**"

Its contribution is the cache-branching technique described in Part 4.1. If
someone says "RCLD" and means a *training* method, they mean 5.1. If they mean a
*Hugging Face repo* on LFM2.5-350M, they mean 5.2.

Both are worth reading. Neither is what we are building; we take the head from
Jev-Omni, the honesty from RCLD, and the scoring-rule theory from Laya.

================================================================================
PART 6 -- THE DESIGN, AND WHY EACH PIECE IS THE PIECE IT IS
================================================================================

6.1 THE FIVE DECISIONS
----------------------
    1. Backbone        LFM2.5-350M (text) or LFM2.5-VL-450M (image)
    2. Readout         last hidden state, one position
    3. Head            Linear(hidden, 256) on 256 POSITIONAL option slots
    4. Objective       cross-entropy (a strictly proper scoring rule) at that
                       position only
    5. Calibration     one fitted temperature per question type

6.2 DECISION 1: WHICH BACKBONE
------------------------------
    Text only, cheapest        -> LiquidAI/LFM2.5-350M
    Text, more headroom        -> LiquidAI/LFM2.5-2.6B
    + image                    -> LiquidAI/LFM2.5-VL-450M
    + image, more headroom     -> LiquidAI/LFM2.5-VL-1.6B
    Text, classifier-native    -> LiquidAI/LFM2.5-Encoder-350M (bidirectional, 8k)
    + audio                    -> LiquidAI/LFM2.5-Audio-1.5B (1.5B, speech only)

Use the *instruction-tuned* checkpoint, not `-Base`, unless you have a strong
reason. Jebadiah measured this directly: the same recipe on the chat checkpoint
with thinking off was worth 2.15 headline points on their 4B -- more than any data
change they made across many experiments.

For a first build: **LFM2.5-350M, text only.** Get the whole pipeline correct,
measure it, and only then add modalities. Multimodal at this scale is a research
project, and we treat it as one in Part 9.

6.3 DECISION 2: WHERE TO READ
-----------------------------
Last token position of the final layer. Three reasons:

  - It is the position the model would have predicted the answer at, so the
    representation is already "the answer so far".
  - It costs nothing: no pooling, no gather, no special tokens.
  - Jev-Omni, Kev, Jebadiah, Laya and this-that-model all read there or
    equivalent. Convergence across independent implementations is evidence.

One subtlety: if you left-pad a batch (which you should, so the last column is
always real), `hidden[:, -1]` is correct for every row with no gather. Our
`collate` left-pads for exactly this reason.

6.4 DECISION 3: SLOT LOGITS vs POINTER SCORING vs LABEL TOKENS
-------------------------------------------------------------
Three designs, all published, all working:

    A. SLOT LOGITS (Jev-Omni; we use this)
       head = Linear(hidden, 256); option i -> slot i
       + cheapest, simplest, handles unseen option words
       - 256 output units regardless of question

    B. POINTER SCORING (Kev)
       score each option's own </opt> hidden state against a <decide> state
       + handles any number of options, richer
       - two forward positions, more machinery, and it needs single-token labels

    C. LABEL-TOKEN LOGITS (Jebadiah, this-that-model, Laya)
       read the LM's own vocabulary logits restricted to the option label tokens
       + reuses pretrained head knowledge
       - needs options that are single tokens; this is Laya's documented
         architectural ceiling on high-cardinality problems

We use A because it is what the model we are copying uses, because it is the
cheapest, and because it is the most obviously correct for a beginner to reason
about. If you later need 500 options, revisit B.

6.4a THE PREREGISTERED EXPERIMENT ON THIS EXACT DECISION
-----------------------------------------------------------
Before you accept any of the three read-out options, read `r-ms/mini-jev`. It is the
only **preregistered** study of this question (`PREREG.md`, amendments v1.1-v1.3),
run on a frozen Qwen3-4B-Instruct-2507 over CLINC150, with every number recomputed
from stored run records. It asks: how much of a Jev-style interface does an ordinary
frozen model already give you, if you read the logits instead of generating JSON?

    "Does reading the letter lose accuracy vs generating JSON under a grammar?
     **No.** 6750 paired observations on 450 texts: JSON 0.909, letters 0.907,
     Δ -0.22 pp, 95% CI [-1.44, +1.04]. **Every k from 2 to 16 has a CI covering
     zero.**"

So the decode-loop saving is close to free on a frozen model. Three further results
change what we would otherwise tell you:

1. **A letter beats writing the option's NAME by +10.0 pp [+8.3, +11.7]** on intent
   classification, and +13.2 pp on domain. Their summary:

       "The single lever that changed accuracy was **giving the model a one-token
        identifier to answer with**."

   This is an argument *for* a symbolic option slot over scoring option text --
   which is what slot logits do.

2. **Never ask the model to write its probabilities as numbers.** Same units, same
   options: letters score **0.896**, a probability-writing format scores **0.346**,
   and 62% of its "choices" are simply the first option. If you have ever seen a
   model emit `{"confidence": 0.91}`, this is the measurement of why that is a bad
   idea.

3. **The caveat that matters most for us.** From their own field table:

       "the shares are **normalized candidate scores, not calibrated probabilities**;
        use the gap for abstention, **do not read the percentage as P(correct)**"

   Reading option logits and calling the result a probability is exactly the mistake
   `fit_temperature` and our per-bucket fits exist to fix. Their setup has no
   temperature fit and no calibration split; ours does. Do not skip it just because
   the numbers look like probabilities.

Speed, measured on the same runs: **4x faster than JSON on short texts**, and
1.4x / 1.8x / 2.4x faster on 2048-token texts *with a shared-prefix cache* -- while
the naive form that re-reads the text per field is **1.10-1.16x slower**. That is
the whole argument for implementing the cached branch (Part 6.8).

One more result to know before you design the interface: a **dependent field** does
better written after the field it depends on, inside one JSON (+5 pp). If question B
genuinely depends on the answer to question A, isolation is costing you accuracy, and
you should put the dependency in the prompt rather than chaining it yourself.

6.5 DECISION 4: THE OBJECTIVE
-----------------------------
    L = - sum_k  target_k * log softmax(W h)_k        (h = last hidden state)

`target` is a distribution over options, summing to 1. Two variants, both
implemented and both worth using deliberately:

  - ONE-HOT for `choice` and `noul`. This is the plain cross-entropy.
  - ORDINAL KERNEL for `score`: put 20% of the mass on each adjacent level.
    For 5 levels with the gold at index 2 you train toward [0, .2, .6, .2, 0].
    This says "level 2 is right, but 1 and 3 are not far off", which is the truth
    about an ordinal judgement. Jebadiah measured the effect: Decision Score on
    human helpfulness went -21.4 -> +11.9, calibration error 0.39 -> 0.045,
    with rubric accuracy unchanged. The model stopped being confidently wrong
    about things it cannot judge.

  - SOFT TARGETS when you genuinely have a distribution. `typed-decisions`
    measured that carrying the soft gold into a learner that could not represent
    one cut KL by a third and score MAE by 15%, with accuracy barely moving.

WARNING from the same field: Jebadiah's 14,714-question synthetic pool, labelled
by their own teacher models, made their 9B *worse*. Soft targets help; bad soft
targets hurt. Prefer human or public labels.

6.6 DECISION 5: CALIBRATION
---------------------------
Fit one temperature per question type on a held-out split, minimising NLL against
the target you trained on -- NOT against the argmax. Jebadiah's own experiment:
the hard-argmax fit sharpens (T 0.68/0.96/0.83) and made their rubric calibration
*worse*; the train-target fit softens (T 1.12/1.33/1.20) and is what they ship.

Our `fit_temperature(logits, targets)` does a 96-point grid search over
T in [0.25, 5.0]. A grid beats LBFGS here: NLL in T is smooth but nearly flat
near the optimum, a grid is dependency-free and reproducible, and 96 points costs
under a millisecond.

You can also ship raw probabilities with `apply_temperature=False`.

6.7 THE PROMPT CONTRACT
-----------------------
The renderer and the head are two halves of one contract. The renderer numbers the
options; the head's slot i is option i+1. Change one, retrain the other.

Our `prompt.py` pins this with a `prompt_sha256`, because every serious
implementation in this field does. Jebadiah stores the source commit and the
hash of a verbatim copy of AINode's renderer, and has a test that checks the copy
against the upstream checkout. Kev ships parity tests. A prompt contract without
a hash is a prompt contract that will silently drift.

Example output, from `render_request`:

    I was charged twice for order 4411.
    subject: "Charged twice"

    ---

    QUESTION: Which team should handle this?

    OPTIONS:
    1. billing
    2. shipping
    3. technical support

    Reply with only the number of the correct option (1-3).
    Output a single number and nothing else.

6.8 QUESTION ISOLATION -- AN HONEST CHOICE
------------------------------------------
Should question B be able to see question A's text?

  - ISOLATED (one forward pass per question): B cannot see A. Matches the
    documented Jev behaviour. Costs one state re-encode per question.
  - JOINED (one pass, all questions in the prompt): faster. But A and B can
    influence each other.

We default to ISOLATED, because "does the customer sound angry" silently
changing "which queue gets the ticket" is a nasty production bug, and because it
is the semantics the ecosystem documents.

The optimisation is a shared KV cache: encode the state once, reuse the cache for
each question branch. That is exactly what RCLD does, and it is what makes the
isolated mode affordable. We did not implement the cached path -- if you need
it, read `rlcd/engine.py` and its `fork_cache` function first; the subtlety is
that you must copy the *convolution* state as well as the attention KV, and that
generic `batch_repeat_interleave` does not handle LFM2's convolution layers.


6.9 ADVANCED CALIBRATION -- WHAT THE PUBLISHED CALIBRATORS ACTUALLY DO
---------------------------------------------------------------------
This section exists because a later pass over the published calibrators changed
what we ship. Three findings, all from real, checked-in calibration files.

6.9.1 TEMPERATURE DEPENDS ON THE OPTION COUNT, NOT JUST THE QUESTION TYPE

`heman10x/rlcd-modernbert-151m` ships a `calibrator.json` with a temperature per
cardinality:

    k=2  -> 5.0069      k=9  -> 1.6668
    k=3  -> 5.0069      k=11 -> 3.3919
    k=4  -> 4.0314      k=17 -> 1.7200
    k=5  -> 3.0560      k=25 -> 1.5144
    k=6  -> 2.3898      global -> 2.8039
    k=7  -> 2.3898

That is a **3.3x spread driven by option count alone**. A single global temperature
is 3.3x too wrong at the ends of the range. (Note k=11 is non-monotone at 3.39 --
per-k fits are themselves noisy at these sample sizes, which is finding 6.9.2.)

So we now bucket. `option_bucket(k)` returns `"2"`, `"3-5"`, `"6-10"`, `"11-20"` or
`"21+"` -- the same buckets the published 0.8B calibrator uses, so our numbers are
comparable with theirs.

6.9.2 SHRINK SMALL GROUPS TOWARD THE GLOBAL VALUE, IN LOG SPACE

The 0.8B calibrator stores, per group, the raw fit `T_raw`, the shrunk `T`, the row
count `n`, and a `weight`. We verified arithmetically that:

    weight = n / (n + 100)

for all 20 of its groups (n=600 -> 0.857142857, n=1000 -> 0.909090909, n=15 ->
0.130434783, n=4233 -> 0.976921302 -- all exact).

And that the blend is **geometric, not arithmetic**:

    T = exp( w * ln(T_raw) + (1 - w) * ln(T_global) )

Reproducing two of its groups:

    general|choice|3-5   T_raw 0.85249625, n 600  ->  0.856385  (published 0.856380)
    intent|choice|11-20  T_raw 0.85304,    n 4233 ->  0.853653  (published 0.853659)

Both match to ~5 decimal places. An arithmetic blend is *also* close on those two
large groups -- but on the n=15 group the two diverge decisively:

    long|choice|2  T_raw 2.53276, n 15 -> geometric 1.01018  (published 1.01016)
                                       -> arithmetic 1.09567

So the geometric blend is the rule. Our `shrink_temperature()` implements it and
`tests/test_smoke.py` checks both reproductions and the arithmetic rejection.

Why this matters: that n=15 group wanted T=5.0 and was rescued only by a hard clamp.
Shrinkage is the principled version of that rescue, and it degrades gracefully to the
global value as n goes to zero.

6.9.3 T CAN BE LESS THAN 1.0

The 0.8B calibrator's global T is **0.880**. That model was *under*confident, so
calibration *sharpened* it. Kev-0.8B needs T=2.35 (overconfident, softened).

**Do not assume T >= 1.** If your grid only searches upward you will never fix an
underconfident model. Ours searches [0.25, 5.0].

6.9.4 FOUR MORE THINGS WORTH COPYING

    FIT OBJECTIVE. One published calibrator names it exactly:
    `"objective": "sample_mean_soft_cross_entropy"` -- cross-entropy against the
    SOFT target, not a one-hot. `bounds: [0.05, 20]`, `calibration_n: 3100`.
    Naming your objective makes your fit reproducible.

    REFIT PER QUANTISATION FORMAT. Same model, same data, two formats:
    BF16 `temperature: 1.0409`, Q4_K_M `temperature: 1.0123`. Argmax agreement
    0.996 for BF16, **0.914** for Q4_K_M. A temperature fitted on one format is
    wrong on another. (This independently confirms Part 12's warning.)

    FOLD IT INTO THE WEIGHTS. Because the score is `h . (w_yes - w_no)` and
    `output_norm` is an RMSNorm gain applied to `h`, dividing that gain by T divides
    the score by T. Zero inference cost, zero extra state, one scalar edit. The
    runtime then uses T=1.0 because it is already baked in. `"temperature_folded":
    true, "folded_tensor": "output_norm.weight"`.

    RECORD THE LOGITS, NOT THE PROBABILITIES. You cannot refit a temperature from
    probabilities alone. Kev's code raises `ValueError("fit temperature on raw
    logits, not previously calibrated outputs")` if you hand it already-calibrated
    outputs. Log the raw logits in your eval harness or you will be stuck.

6.9.5 AND THE BIGGEST SINGLE WIN WAS A BUG FIX

`Verdict-open-jev`'s README is worth reading for this:

    "The engine previously failed to load `calibrator.json` during standalone
     instantiation, running at uncalibrated temperature 1.0. A scope check also
     limited calibration exclusively to 5-candidate queries, leaving other
     cardinalities unscaled."

Fixing that moved hard-tier ECE from **0.298 to 0.118 (-60.4%)**. The largest
calibration win in that project's history came from *loading* the calibrator
correctly, not from fitting it better. Check yours loads.

6.10 FOUR FINDINGS THAT CHANGE THE DESIGN (from a later pass)
------------------------------------------------------------
These arrived after the core design was written and each one should change what you
do. They are the reason this section exists.

6.10.1 WE TESTED IT. ON OUR CONFIGURATION, THE LAST LAYER WON.

Nokia's AnyJev (github.com/nokia-applied-research/AnyJev, with Tencent Hunyuan,
Apache-2.0) reports:

    "Cutting Qwen2.5-7B from 28 blocks to 18 left accuracy slightly HIGHER and
     calibration better, and was faster: a middle block is a better feature space
     for a linear head than the last one, where the remaining blocks are busy
     turning the answer into tokens."

    "Depth is usually a gain, not a trade."

**WE RAN THE EXPERIMENT. IT DOES NOT REPLICATE HERE.**

Frozen LFM2.5-350M, a fresh head trained per layer so the read-out layer is the ONLY
variable, real `typed-decisions` data with soft gold distributions, temperature fitted on
one half of a held-out set and reported on the other:

    layer        train loss   acc     brier    ece      T
    L0  (-16)    1.2877       0.4000  0.1360   0.2258   0.350
    L4  (-12)    1.2875       0.4000  0.1360   0.2256   0.350
    L8   (-8)    1.2760       0.4000  0.1358   0.2268   0.600
    L12  (-4)    1.2665       0.4000  0.1346   0.2203   0.750
    L15  (-1)    1.2508       0.4889  0.1312   0.1360   0.900

**The last layer wins on accuracy, Brier, ECE AND training loss**, and the fitted
temperature rises monotonically with depth -- meaning the earlier layers are more
overconfident relative to how often they are right.

How much weight this carries: **n=45** evaluation questions, so the accuracy gap is 4
questions. What carries it is that four independent indicators agree and the temperature
trend is monotonic, not the accuracy delta alone. And absolute accuracy is low (0.4889
against a ~0.470 Prior base-rate baseline) -- this is a 198-example, head-only,
frozen-backbone probe, so the claim is about *which layer*, not about achievable
accuracy.

AnyJev measured a **7B** model. The "top blocks are busy turning the answer into tokens"
mechanism may simply be weaker at 350M.

**So `readout_layer=-1` stays the default.** The knob is still there and worth sweeping
on YOUR data, but the honest statement is now "we tested it and found nothing better"
rather than an open question.

Full write-up: `.deep-research/notes/04-layer-sweep-results.md`.
Reproduce: `python experiments/layer_sweep.py`

One more reason to sweep it yourself: our probe froze the backbone. A LoRA-tuned model
reshapes the layers, and the optimum could move. Our result rules out the *frozen*
350M case; it does not rule out a tuned one.

6.10.2 A CLOSED-FORM HEAD BEATS LoRA WHEN YOU HAVE 100-300 LABELS

AnyJev's L2 level fits a head per question in closed form, in seconds, with **no
gradients and the model's weights untouched**. Reported on BANKING77 20-way:

    labels needed          none    100-500
    answer flips on reorder 0.230    0.073    0.077
    accuracy                0.747    0.803    0.807
    calibration error       0.240    0.184    0.095
    AUTO-DECIDABLE at <=5% error   7.7%    46.3%    52.0%

Read the last row twice. Accuracy moves six points, but the share of traffic you can
safely automate goes **7.7% -> 52.0%**. That is the entire argument for this class
of model in one table: with raw logits a "0.9" is not trustworthy enough to act on,
so everything goes to a human; once the probability means something, you can set a
threshold.

**Practical consequence: do a closed-form fit BEFORE you reach for LoRA.** It is
minutes of work, it needs almost no data, and it gives you a baseline that tells you
whether the backbone's features are usable at all. If a linear head on frozen features
cannot separate your classes, LoRA will not rescue it.

6.10.3 ORDER-FLIP HAS A ZERO-LABEL FIX

AnyJev's L0 level changes **only the readout** -- no labels, no training -- and moves
the order-flip rate from 0.230 to 0.073 while *also* raising accuracy 0.747 -> 0.803.

This is the third independent confirmation that the readout geometry matters (after
the option-name paper and Laya's Banking77 ceiling). If your small model is
order-sensitive, try fixing the readout before you fine-tune anything.

6.10.4 THE CURRENT TOP OF THE LEADERBOARD IS CALIBRATION-BOUND

7.2 TWO REAL BUGS THAT ONLY RUNNING THE CODE FOUND
---------------------------------------------------
Worth reading, because you will hit both.

BUG 1: THE CAUSAL-LM WRAPPER RETURNS LOGITS, NOT HIDDEN STATES.
    `Lfm2ForCausalLM(...)(input_ids=...)` returns `logits` of width 65,536. Our
    head expected 1,024 and raised. The fix is `resolve_backbone()`, which unwraps
    to the inner `Lfm2Model`. The guard is deliberate: silently broadcasting a
    vocab-wide tensor into a decision head produces a model that trains without
    error and is completely wrong. We validate the width and name the fix.

BUG 2: RAGGED TARGETS DO NOT BROADCAST.
    A batch with 2-option and 5-option questions produces targets of width 2 and
    5, which cannot be multiplied against a fixed-width logit tensor. `collate`
    now pads targets to the batch's widest option count and the loss narrows the
    logits to match. The padded logits are -1e30, so the dropped terms contribute
    exactly zero.

A third, found by writing a test against a published example: the score-confidence
denominator D must use the *declared* number of levels, not the number with
non-zero probability. A level the model assigned exactly 0.0 is still in the
legend. The wrong version returned 0.12 where the published example says 0.34.

8.0 ENVIRONMENT
---------------

8.1 STEP 1: PROVE THE BACKBONE LOADS
-------------------------------------
Before writing a line of training code:

    python tests/test_integration.py

It loads pinned LFM2.5-350M weights, installs the hook, runs noul/choice/score,

8.2 STEP 2: BUILD YOUR DATA
---------------------------
One JSON object per line:

    {"state": "I was charged twice for order 4411.",
     "questions": {
       "team":   {"type": "choice",
                  "instructions": "Which team should handle this?",
                  "options": ["billing", "shipping", "technical"],
                  "label": 0},
       "urgent": {"type": "noul",
                  "instructions": "Does this need urgent attention?",
                  "label": 1}}}

`label` is the INDEX of the correct option. For `score` you may use a dict:

    "label": {"index": 2, "soft": [0.0, 0.1, 0.7, 0.2, 0.0]}

WHERE THE DATA COMES FROM -- and this matters more than the training code:

BEST (Apache-2.0, ships gold distributions):
  - `LocalLLaMA/typed-decisions` -- 1,600 cases, 4 workflows
    (agent_trace_observability, customer_service, invoice_processing,
    security_incidents), 5 questions each, GOLD PROBABILITY DISTRIBUTIONS
    included (mean of 3 teacher samples at temperature 0.7). This is the best
    training set in the ecosystem for a first build, because the soft targets are
    the point.
  - `akhilaaa3/decision-bench` -- 293 questions, 2 subsets, held OUT for eval.

GOOD, AND WORTH KNOWING ABOUT:
  - `nvidia/HelpSteer2` (CC BY 4.0), `mteb/summeval` (MIT) -- human-rated
    scores, the right source for `score`-question targets.
  - `google/boolq`, `nyu-mll/glue`, `fancyzhx/ag_news`, `CogComp/trec` --
    plain hard labels.

BEST FOR TEACHING A SMALL MODEL *UNCERTAINTY* (this is the one most people miss):

  - `tasksource/procedural-typed-decisions` -- **Apache-2.0**, 12 configs, 100K-1M
    rows, and the crucial property: **"Every answer is computed exactly from the
    state by rules that the state itself spells out."** No noise, no annotator
    disagreement.

    Some configs emit **exact posteriors, not one-hots**. `random_is_deposit` and
    `random_is_long` give the exact probability k/n. `partial_observation_calibration`
    gives a genuine Bayesian posterior over a partial view. `policy_under_uncertainty`
    gives "exact posteriors over a role known through history counts and reports of
    stated reliability".

    Why this matters enormously for a 350M model: it cannot learn "express
    uncertainty when the evidence is incomplete" from real support tickets, because
    real tickets rarely come with a known answer distribution. Here it is exactly,
    noiselessly available. Difficulty `level` 0-4 scales events, records, sensors and
    distractors. States are unique within a split and never shared between
    train/val/test. Generation is deterministic.

    Its schema is already the System One request shape: `state` plus `questions` with
    `type` / `instructions` / `criteria`, and `answers` in System One shape.

  - `tasksource/tasksource-jev-typed-decisions` -- 2.5M train / 15k val / 15k test,
    Apache-2.0-ish with a **per-row `license_use` field** you can filter on
    (`ds.filter(lambda use: use=="commercial", ...)`). Features include
    `options: list<string>` and `target: list<float64>` -- a runtime-varying K with
    an already-materialised distribution, which is exactly what a 256-slot head
    wants. Soft targets appear where the source has >=5 annotators per item; graded
    data is 10% of the mix.

    CAVEAT: its `license_use` treats share-alike as "commercial", so a commercial
    filter does NOT mean "no copyleft obligation". Check the underlying licence.
    Also: the procedural rows are embedded inside it, so training on both
    double-counts that 10% slice.

AVOID as a first move: a large pool of LLM-generated labels. Jebadiah's
14,714-question synthetic pool made their 9B worse. Synthesise to *cover gaps in
real data*, not to replace it.

SIZE. Kev trained 0.8B/4B/9B on 10,000 public records for two epochs in ~20
minutes on one H100. Jebadiah's 4B used 11,013 records / 15,813 questions for one
epoch, 67 minutes on an A100. Jev-Omni used 24,000. For a 350M with LoRA,
**10k-30k examples is a reasonable target**, and you will get most of the benefit
from the first 2,000 if they are clean and in-distribution.

8.3 STEP 3: TRAIN
-----------------

        --backbone LiquidAI/LFM2.5-350M \
        --revision 9e6c6ccf47cd318696e137d381a7ded8fe4df09f \
        --data train.jsonl \
        --calibration calib.jsonl \
        --out runs/jeb-nano \
        --epochs 2 --batch-size 8 --lr 1e-4 --head-lr 1e-4 \

RECOMMENDED STARTING HYPERPARAMETERS, and where each comes from:

    LoRA r=16, alpha=32, dropout 0.05   Kev and Jebadiah both use exactly this.
    target_modules = "all-linear"      LFM2.5 is hybrid: 10 of its 16 layers are
                                       convolutions with their own projections. An
                                       adapter that only touches q/k/v/o leaves
                                       most of the network frozen. Kev's trainer
                                       picks targets from the model config for the
                                       same reason.
    lr 1e-4 (head also 1e-4)           Kev uses 1e-4 at 0.8B, 5e-5 at 4B/9B.
                                       Jebadiah uses 1e-4. A 350M can take 1e-4.
    2 epochs                           Kev: 2. Jebadiah: 1, and explicitly reports
                                       "two epochs were worse than one" in an
                                       earlier experiment. Start with 1, try 2.
    batch 8, bf16                       Kev's exact setting.
    schedule                            linear warmup (10%) then linear decay to
                                       10% of peak -- Jev-Omni's schedule.
    seed                                fix it and record it.

8.2a WE MEASURED WHETHER LoRA ACTUALLY HELPS. IT DOES -- A LOT.
----------------------------------------------------------------
The whole design assumes you must fine-tune the backbone rather than just fit a
head. We ported that from Kev and Jebadiah and never tested it. So we tested it:
same data, same splits, same eval, read-out at L15. The only thing that changed
is whether the backbone's weights can move.

    arm                                acc     brier     ece      T   cov@5%  cov@20%
    A  frozen backbone + head       0.3233   0.1404  0.1467  3.300   0.0000    0.0000
    B  LoRA r=16 all-linear + head 0.5633   0.1098  0.0646  1.050   0.0967    0.3367

Scope: single seed (17), not replicated. A seed-42 replication is running but is blocked by host load (load average 93) and may not complete. Read the accuracy and temperature figures below as order-of-magnitude, not point estimates. The coverage gap (0.0000 vs 0.0967 at n=300) is the least noise-prone claim, since a zero is hard to produce by accident. See `notes/12-seed-robustness-pending.md`.

**24 accuracy points, and the frozen model auto-decides NOTHING.** For scale,
`typed-decisions` puts a base-rate Prior at 0.470. Arm B clears it; arm A does not.

    THE BAR IS 0.766, NOT 0.5633.

`typed-decisions` is 2,000 decisions across four workflows -- the same data our
probe scores on. An Apache-2.0 checkpoint at our size class already exists:

    laya-typed-decisions (421M, open weights)   0.766
    base laya zero-shot (421M, open weights)    0.362
    our LoRA arm (354M, 360 training questions)  0.5633
    our frozen arm (354M)                        0.3233

Trained by a different person, on ONE RTX 6000 Pro (96 GB), on a fully
human-annotated corpus. We are ~20 points below that, on CPU, with 360
training questions and 3 epochs.

Read this the right way. Our findings are about METHOD -- frozen vs LoRA,
coverage at a 5% budget, thresholds not transferring between workflows --
and none of them need to be state of the art to be true. But 0.5633 is not
a result to be proud of on its own. If you are building this, 0.766 is the
number to beat and the weights to borrow are already public.

One operational warning worth stealing from that model card: laya ships
with a 1,024-token default that SILENTLY TRUNCATES long documents. It says
so in bold. Make sure your context handling is as loud about it.

**But the more interesting number is the temperature: 3.300 -> 1.050** (and 4.150 ->
0.850 on `invoice_processing`). A large
fitted T means the raw logits are far more confident than the accuracy
justifies. So the frozen model does not just score worse, it scores
**dishonestly** worse. LoRA fixed the calibration, not only the argmax.

That is the concrete mechanism behind jev-lite's "accuracy was flat from step
250 while ECE fell 0.086 -> 0.019: the model did not learn to be right more
often, it learned to be honest about when it isn't."

PRACTICAL CONSEQUENCE: if you ship a head-only model, the number you threshold on
is not meaning what you think. Fit LoRA. And watch the fitted temperature -- if
it comes out near 1.0 your model is close to self-calibrating; if it is 2+,
you have a calibration problem regardless of your accuracy.

CAVEATS, so you do not over-read it: n=45 evaluation questions, one workflow
of four, 198 training questions, 3 epochs, on CPU. This is a feasibility probe,
not a tuned result -- published work uses 10k-24k examples. The claim is the
DELTA between arms, not the endpoint.

Reproduce: `python experiments/lora_vs_head_only.py`
Full write-up: `.deep-research/notes/05-lora-ablation-results.md`

HOLD OUT YOUR CALIBRATION SPLIT. If you do not pass `--calibration`, the trainer
takes 5%. It must be split BY FAMILY, not randomly by row, so sibling records
never straddle the boundary -- Jebadiah does this by family hash and it matters
when your data has near-duplicates.

8.4 STEP 4: THE ORDINAL TARGET IS ON BY DEFAULT FOR `score`
-----------------------------------------------------------
`_ordinal_target(2, 5)` returns `[0, 0.2, 0.6, 0.2, 0]`. Twenty percent of the
mass goes to each adjacent level; the label keeps the rest. At an edge,
`_ordinal_target(0, 3)` = `[0.8, 0.2, 0]`.

This is the single highest-leverage training decision in the whole guide, and it
is measured: Jebadiah's HelpSteer2 Decision Score went from -21.4 to +11.9 and
calibration error from 0.39 to 0.045 when they added human-rated score data and
switched to an ordinal target. Rubric accuracy did not move. The model became
honest about not knowing.

8.5 STEP 5: WHAT THE TRAINER PRINTS, AND WHAT IT MEANS
------------------------------------------------------
    resolved backbone : Lfm2Model
    trainable: LoRA 5,996,544 + head 8,200 = 6,004,744 parameters

6.0M trainable out of 354.5M = 1.7%. If that line says LoRA 0, your
`target_modules` matched nothing and you are training a randomly-initialised head
against a frozen model. The trainer warns about exactly this.

8.6 STEP 6: MERGE (OPTIONAL)
----------------------------
Jebadiah merges with `W' = W + (alpha/r) B A` shard by shard on CPU in fp32,
stored in bf16, then verifies by re-scoring: 259 of 260 questions gave the same
pick, and the largest probability difference was 0.0190 (median 0.0021), which is
bf16 across two devices.

Keep the adapter separate. It is 6M parameters instead of 354M, and merging buys
you only a small speedup.

PART 9 -- MULTIMODAL, HONESTLY ASSESSED
================================================================================

You asked for image, audio and video, like Jev-Omni has. Here is the honest

9.1 WHAT IS ACTUALLY HARD
-------------------------
The head is not the hard part. The hard part is the *encoder budget*.

Jev-Omni's vision tower emits up to 280 soft tokens per image. For a 16-frame
video that is 4,480 visual tokens before a single word of text. Against
LFM2.5-350M's 32,768-token context that is 13.7% of the window; against Gemma
4-12B's 262,144 it is negligible.

**The smaller your text model, the more painful the visual token budget becomes.**
That is the core tension, and it is why LFM2.5-VL-450M exists.

9.2 THE GOOD NEWS: LIQUID ALREADY SHIPPED A 450M VISION MODEL
-------------------------------------------------------------
`LiquidAI/LFM2.5-VL-450M` is LFM2.5-350M plus a **SigLIP2 NaFlex 86M** vision
tower. Its config:

    text_config   hidden_size 1024, 16 layers, vocab 65,536  (the same 350M)
    vision_config hidden_size 768, 12 layers, 12 heads, patch 16, num_patches 256
    projector_hidden_size 2048, downsample_factor 2
    min_image_tokens 64, max_image_tokens 256, min_tiles 2, max_tiles 10
    tile_size 512, use_thumbnail true, image_token_id 396

So the visual path is already built and already lands in your 1024-wide backbone.
You do not have to invent a projector. Its benchmarks (VLMEvalKit): MMStar 43.00,
RealWorldQA 58.43, MMBench 60.91, POPE 86.93, BLINK 43.92, RefCOCO-M 81.28.

And there is a task-specific sibling: **`LiquidAI/LFM2.5-VL-450M-Extract`**,
tuned to return user-defined fields as JSON. On a 2,000-sample
(image, schema, JSON) benchmark: JSON validity 98.9, schema F1 98.8, VLM judge
84.5 -- beating InternVL3.5-1B (98.0/96.5/80.7) and Qwen3.5-2B (97.9/97.7/89.7)
while being 4x smaller.

Read that table as the strongest available evidence that a sub-1B multimodal
model can do genuinely useful, structured work.

9.3 THE PLAN, IN ORDER
-----------------------
PHASE 1 (do this first): text only, LFM2.5-350M, full pipeline, measured.
PHASE 2: swap the backbone to LFM2.5-VL-450M. Change `AutoModelForCausalLM` to
         `AutoModelForImageTextToText` and `AutoTokenizer` to `AutoProcessor`.
         `JebNanoModel` already branches on `model_type` containing "vl" and
         already has a `_build_inputs` media path.
PHASE 3: collect image decision data and LoRA-tune the projector + backbone.
         Start from the Extract nano's prompt convention (a YAML field list in the
         system prompt) rather than inventing one.
PHASE 4: audio. There is no small Liquid audio decision model. LFM2.5-Audio-1.5B
         is 1.5B, speech-only, and built for generation, not decisions. You would
         be building a new audio tower. Do not start here.
PHASE 5: video. 16 frames = 16 image encodes. Jev-Omni's own reported cost is
         504 ms for 16 frames on an H200, versus 83 ms for text. Video is ~6x
         the cost of text at the 12B scale and proportionally worse for you,
         because your text model has a much smaller context to amortise the
         frames over. Do video last, or not at all.

9.4 AUDIO, IF YOU MUST
----------------------
Match Jev-Omni exactly so your numbers are comparable to published ones:

    ffmpeg -v error -y -i input -t 30 -ac 1 -ar 16000 out.wav

16 kHz mono, 30 s cap. That gives 480,000 samples. Whisper's front end uses
hop_length 160, so 100 mel frames per second, 3,000 frames for 30 s -- but
Whisper's encoder only consumes 1,500 positions (15 s) per forward pass, and
longer audio is chunked.

Jev-Omni's own audio encoder config: `audio_embed_dim 640`,
`audio_samples_per_token 640`, i.e. 16,000/640 = 25 audio tokens per second, and
`audio_seq_length 750` for 30 s.

For reference on how small you could go: whisper-tiny is 39M (d_model 384,
4 encoder layers), whisper-base 74M (d_model 512, 6 layers). Either projects into
1024 with a linear layer.

9.5 A REALITY CHECK ON THE BENCHMARKS
-------------------------------------
    MMAU   10,000 questions, 27 tasks, speech + music + sound, one third music.
           Gemini Pro v1.5 scores 52.97%. Qwen2-Audio 52.50%. Jev-Omni scores
           63.10% on the 1,000-question mini split.
    MVBench 20 temporal tasks the authors say "cannot be effectively solved with a
           single frame", 4,000 questions. Jev-Omni 53.10% on 14 tasks.

MMAU is brutally hard. If you get 40% on it with a 450M model, that is a real
result, not a failure. MVBench at 53% is close to what a 12B gets.

9.6 IF YOU SKIP ALL OF THIS
---------------------------
A text-only Jeb-Omni-Nano is a genuinely useful product: ticket triage, routing,
guardrails, moderation, structured extraction, LLM-vs-small-model cascades. Kev
ships exactly that and calls it a fast base to specialise. You can ship that on
Tuesday.

PART 10 -- EVALUATION, AND THE FIVE WAYS TO LIE TO YOURSELF
================================================================================

10.1 WHAT TO REPORT -- AT MINIMUM
---------------------------------
    accuracy           argmax correctness
    Brier              distribution quality (report it even if ECE looks fine)
    KL to gold         if you have gold distributions (typed-decisions does)
    ECE (state the binning)
    mean confidence    so the reader can see over/under-confidence directly
    coverage @ error   the share of decisions you can automate at a 5% error
                       budget. THIS is the number your users actually care about.

`typed-decisions` has the sharpest framing of the coverage number, and it is
worth stealing: their leaderboard is sorted by accuracy, KL, Brier, latency and
price per million input tokens, and their "Prior" row -- a model that predicts
each question's base rate while ignoring the input -- beats the ModernBERT
specialist on ECE. Guessing the base rate is perfectly calibrated by
construction. That is the clearest possible argument that ECE alone is not a
quality metric.

10.2 THE FIVE PITFALLS
----------------------
PITFALL 1: COMPARING COSTS PER TOKEN
    The Cost column in JevBench is dollars per 1,000 DECISIONS, not per 1,000
    tokens. One decision is a whole question: state, rubric, options -- hundreds
    to thousands of input tokens. Jev reads ~950 input tokens per decision, so at
    $0.042/M, 1,000 decisions cost $0.0399. Getting this unit wrong is the single
    most common error in this field.

PITFALL 2: COMPARING ACROSS REQUEST SHAPES
    DecisionBench withdrew a chart because of exactly this. Jev-Omni and Jev were
    sent ONE REQUEST PER QUESTION (state re-sent every time); three chat models
    were sent ONE REQUEST PER STATE (all of a state's questions together, which is
    their natural shape and genuinely cheaper for them). That made Jev look ~3x
    cheaper than it is. The dataset authors then measured the true multiplier:
    splitting a state into per-question calls multiplies input tokens by 2.82x
    on medium and 3.09x on hard.
    RULE: state your request shape next to every number.

PITFALL 3: SPECIALIST vs GENERALIST
    A specialist is fitted per workflow and cannot answer an unseen question. A
    generalist handles arbitrary schemas zero-shot. Their scores are NOT
    comparable. `typed-decisions` states it: "Jev at 0.727 against the specialist's
    0.646 has not beaten it by eight points... Read the gap as the price of
    generality, not as a quality ranking."
    RULE: say which mode you are.

PITFALL 4: IGNORING OPTION ORDER
    This is the big one, and there is now hard evidence that it is not a rounding
    error. See Part 11.

PITFALL 5: EVALUATING ON TRAINING DATA
    Kev-0.8B's card is a model of honesty here: it reports that JevBench's public
    items, which no training or selection step saw, give a paired gain of
    "+2.7 pp [-1.8, +7.2]: not distinguishable from zero" on the hard tier, even
    though the same checkpoint gained +26.9 pp on its in-distribution test. It
    also notes an eval-only source that got *worse* (When2Call fell from 0.233 to
    0.133) and says "do not use this checkpoint for tool-call routing."
    RULE: keep a locked test set, read it once, and report the un-flattering rows.

10.3 THE EVALUATION YOU MUST RUN: OPTION-ORDER ROBUSTNESS
----------------------------------------------------------
Our `prompt.py` ships `permute()` for this.

    for order in itertools.permutations(range(q.n_options)):
        p = permute(q, list(order))
        answers.append(model.decide(state, p))


Report the fraction of questions whose *prediction* changes. JevBench's
`open-alternative-jev` row: with the author's option order the model scored 21%;
with the options reversed, 72%. Small models are very sensitive to option order.

Kev reports an option-order flip rate of 0.07-0.08 for its small models and
0.00 for Jev. If your flip rate is above ~0.10, do not ship a threshold policy
until you have fixed it.

10.4 MEASURE LATENCY HONESTLY
----------------------------
RCLD's own methodology is the template and it is unusually careful:

  - two untimed warmups, then three measured repetitions
  - `perf_counter` with device synchronisation before and after the whole request
  - includes tokenisation, cache copying, all forwards, selection, JSON
    assembly; excludes model loading
  - method order alternated, case order seeded and shuffled
  - "Repeated deterministic answers do not create additional independent accuracy
    examples."
  - "Small-sample p95 estimates are descriptive."

And its headline caveat, which you should copy into your own card:

    "This isolates an inference-method comparison; it does not establish the
     fastest attainable backend on any hardware."

Also: the MLX 4-bit Jev-Omni card reports that the published H200 numbers are
"not transferable" to a Mac mini, and that its own temperature fit made HELD-OUT
ECE worse (0.06261 -> 0.06774) even though the fit split improved. That is why
you fit temperature on a split and evaluate on a different one.

================================================================================
PART 11 -- WHAT WILL GO WRONG
================================================================================

We go in order of how likely you are to hit it.

11.1 THE OPTION-NAME FAILURE -- READ THIS ONE TWICE
----------------------------------------------------
There is a paper specifically about this, published 2026-09-22:
"Type-Safe Is Not Error-Free: A Constrained Decision Head Follows the Option Name,
Not the Rubric Bound to It" (arXiv 2609.26758).

The experiment: keep the question, the state, the rubric wording, and the SET of
option names exactly the same, and change only WHICH NAME IS BOUND TO WHICH
RUBRIC. Renaming two options from "0"/"1" to "no"/"yes".

The result, on 1,200 workflow decisions across 4 predicates:

    70.4 more answers changed per hundred   (95% CI [67.6, 73.1])
    AUC moved from .94 to .23

AUC below 0.5 is not noise. It is a *systematic ranking reversal*. The model has
stopped reading the rubric and started reading the name.

The findings that make this actionable:

  - The effect is at least 7.4x larger than a neutral-name control, across all
    four predicates, and GROWS with the number of options.
  - It depends on read-out geometry: a second model family that mean-pools over
    the full option span flips 4.1x LESS often. (This is an argument against the
    pointer-scoring design in Part 6.4, and we think it is the strongest
    published argument in the ecosystem for slot logits.)
  - The hosted Jev has it too: AUC .8146 -> .5806, 24x its test-retest flip floor.
  - Replacing the option names with RANDOM CHARACTER STRINGS returns every model
    family to the neutral regime, with no accuracy loss.

WHAT TO DO ABOUT IT:

  1. RUN THE TEST. Rename your options, re-run, and measure the AUC delta. It
     takes an hour and it is the highest-value hour in your project.
  2. If you are affected, consider neutral or random-ish option identifiers in
     the prompt, with the human-readable name carried in the rubric. The paper
     shows this fixes the failure at no accuracy cost. This is a prompt change,
     not a retrain.
  3. Keep the option count small. The effect grows with cardinality. Jev-Omni
     itself says it is "best supported at ≤20 options", and Laya's docs say
     "keep choice questions under ~20 options."
  4. Note that the type-error rate stays 0% throughout. A model can be
     perfectly well-typed and completely wrong. Schema conformance is not a
     correctness signal.

11.2 THE VOCABULARY LOGIT TRAP
-----------------------------
If you use the label-token design (Jebadiah/Laya/this-that), the head competes
with 65,536 vocabulary logits, and high-cardinality option sets break it. Laya
scores 0.425 on Banking77 (77 labels) against Jev's 0.870, and their own
diagnosis is architectural: options share a fixed token budget, so 77 labels get
~3-4 tokens each and become indistinguishable. Both Laya checkpoints score
*exactly* 0.425 -- a budget ceiling, not a capability gap.

Our slot design does not have this failure mode. That is a second, quieter
argument for it.

11.3 PRECISION LOSS UNDER QUANTISATION
--------------------------------------
Quantising a 12B decision model to Q4 broke its calibration. The GGUF card for
Jev-Omni-Q4_K_M says plainly:

    "this Q4 matched the winning option on 3/4 published text verification
     examples; the maximum absolute probability difference was 0.210. Do not
     assume source-equivalent probabilities or calibration."

RULE: after any quantisation, re-measure ECE and Brier against the unquantised
model. If they moved, refit the temperature for the quantised model. Do not ship
a calibration number measured in a different precision than the one you serve.

11.4 CALIBRATION TRANSFERS TO NOTHING
-------------------------------------
Kev-0.8B, in as many words:

    "Probabilities are usable in-domain; treat them as advisory elsewhere."
    "Out-of-domain Brier / ECE 0.430 / 0.049" while "in-distribution ECE 0.033".

Same model, ECE 0.033 in-distribution and 0.049 out, and a Brier of 0.430. Fit
your temperature on YOUR data. There is no such thing as a temperature that
transfers.

11.5 HIGH-CARDINALITY AND THE 20-OPTION CEILING
-----------------------------------------------
    Jev-Omni's own card: "Best supported at ≤20 options. The head accepts 256,
    but quality above 20 is not established."
    Laya's docs: "Keep choice questions under ~20 options."
    JevBench documents a 21% -> 72% swing from reversing a 2-option list.

20 is not a round number someone picked. It is where the evidence stops.

11.6 SUB-1B MODELS TRAIL ON KNOWLEDGE
--------------------------------------
Kev-0.8B, per-source, out of domain:

    QNLI 0.85 / Jev 0.93       SciQ 0.91 / 0.99
    MMLU 0.42 / 0.90           PAWS 0.55 / 0.79
    3-level date arithmetic 0.38 / 0.93

Date arithmetic at 0.38 is barely above the 0.33 chance rate for three levels --
the model hedges to the middle. Their own note: "Ordinal hedging on date
arithmetic: collapses to the middle level."

RULE: a small decision model is excellent at classification-shaped questions and
poor at anything requiring knowledge or precise arithmetic. If you need those,
cascade: small model decides, large model handles what it flags.

11.7 STACKING LoRA DELTAS IS NOT FREE
--------------------------------------
Kev-0.8B needed fifteen registered training rounds. One attempt to stack a skills
delta on top of a documents delta failed: "the second delta eroded the first:
seed 1's documents lower bound was -2.03 pp against a -2 pp floor." A later
joint-training round succeeded where sequential stacking failed.

RULE: if you fine-tune twice, consider training on the union instead.

11.8 THE TEMPERATURE CAN HURT
-----------------------------
The MLX 4-bit card: temperature scaling improved ECE on the fit split
(0.06261 -> better) and made held-out ECE WORSE (0.06261 -> 0.06774).

RULE: always report calibration on a split you did not fit on.

11.9 THE THREE SECURITY PAPERS. READ THESE BEFORE YOU SHIP.
-----------------------------------------------------------
A decision model takes untrusted text and returns a number your software acts on.
That is an attack surface, and three September 2026 papers document it. None of these
are hypothetical.

(a) NATURAL CONTEXT CAN FLIP DECISIONS -- arXiv 2609.30243 ("JevOut")
    They define a wrong target option per initially-correct item, then let the
    model's OWN option probabilities guide fluent-sounding context additions that
    keep the source, question, choices and gold answer intact.

        312 of 508 initially-correct decisions redirected (61.4%)
        in 229 cases the model gave the wrong target >= 0.7 probability
        three other decision systems: 64.9%-73.2% targeted flip rate

    Their conclusion: "short, ordinary-looking context can shift a correct choice
    to a high-confidence wrong one... this sensitivity raises concerns about
    treating their probability outputs as reliable decision interfaces."

    This is a direct attack on the contract this whole guide is built on. Your
    `state` field is a blob of user text.

    RULE: treat the state as adversarial input. Sanitise it, and if the state
    includes free-form user text that a human also reads, do not let the model's
    probability be the only thing standing between that text and an action.

(b) ADAPTIVE ATTACKS GET CHEAPER AGAINST PROBABILITIES -- arXiv 2609.28613
    "Decision Hijacking" ran 510 reconstructed InjecAgent cases. Malicious content
    shifts action probabilities but rarely selects the attacker's target outright.
    The problem is the feedback channel:

        adaptive attacks using score feedback DOUBLE the mean highest
        attacker-target probability found during optimisation
        success on fresh validation: 1.8% -> 3.5%

    Their conclusion: "schema-defined outputs change but do not eliminate
    prompt-injection risk."

    Read that as: by returning a calibrated score you have built a gradient
    oracle against yourself. Anyone who can submit inputs and read probabilities
    can optimise against your model far more cheaply than against a text
    generator, whose output is a much noisier signal.

    RULE: if your model is reachable by an adversary, rate-limit, and do not
    expose per-option probabilities to untrusted callers. Return the argmax and a
    coarse band.

(c) CASCADES FAIL WHEN ERRORS ARE CORRELATED -- arXiv 2609.29769
    This one undercuts the most common deployment plan, which is "small model
    decides, escalate the uncertain ones to a big model." They compared Jev with
    LLM judges on nine panels and found:

        "Jev's confidence ranks its own errors on most panels, which should make a
         cheap classifier the ideal first stage of a cascade" -- BUT --
        "Correlated errors undo that advantage. The LLM judges repeat nearly all
         of Jev's most confident errors, so a cascade replayed on the recorded
         verdicts lowers cost but gains at most 1.5 points over the best single
         judge with cross-fitted thresholds, and at most 2.0 even with oracle
         thresholds."

    So the escalation buys you almost nothing, because the big model makes the same
    mistakes on exactly the cases you escalated.

    A companion paper (arXiv 2609.26550) found the opposite on a different
    benchmark, where a frozen cascade retained 99% of a state-of-the-art judge's
    accuracy at lower cost. **The two are in direct tension, and the difference is
    benchmark-dependent.**

    RULE: measure your cascade end to end, with cross-fitted thresholds, on YOUR
    data. Do not assume escalation works because it works in someone's blog post.
    Check whether your fallback model actually disagrees with you on the cases you
    escalated.

(d) A CAVEAT ON OUR OWN DESIGN CHOICE
    "Visual Jev" (arXiv 2609.25845) reports: "A matched typed-head control offers no
    consistent accuracy advantage over the language-model-head readout." That is
    evidence against adding a bespoke typed head -- and we add one anyway, because
    the same paper's conclusion is "adapt the backbone for quality, retain the
    existing readout, and share execution for efficiency," and because slot logits
    solve a specific problem the LM-head does not (option words that are not single
    tokens, and the 77-option case where Laya's label-token approach hits a hard
    0.425 ceiling). We are choosing on a trade-off, not claiming the head is free of
    downside. Test both readouts on your task if you have the budget.

11.10 A MODEL CAN READ A NEGATED RULE AS ITS OPPOSITE, CONFIDENTLY
----------------------------------------------------------------
This one should worry you more than the option-name failure, and it comes from the
same architecture family ours is.

`flock-io/this-that-model` went 1.0 -> 1.1 -> 1.2, and the 1.1 -> 1.2 changelog
describes the worst failure mode we have found in any of these systems:

    "1.2 fixed *how the rule is written*. 1.1 read `bays without chilled handling
     are ineligible` as though it named the eligible set -- **not failing to apply
     the rule but applying its opposite, at 0.88 mean confidence.**"

Read that twice. The model did not fumble the rule, hedge, or refuse. It computed the
**inverse** of the correct answer and returned it with 88% confidence.

They then measured the same rule written eleven ways, against a chance rate of 0.19:

    1.1   ranges 0.00 to 0.89     <-- four of eleven rows sit BELOW chance
    1.2   ranges 0.98 to 1.00

Below chance is not guessing. It is systematically wrong in a specific direction.

Note the context: this is the model that scores **0.941 accuracy / 0.042 Brier** on
the 68-question cohort that the Jev comparison uses. It is a leading system. And it
inverted a negation.

WHY THIS HAPPENS. A slot-logit or label-token readout has to compress "this option is
excluded by a condition" and "this option is named by a condition" into a single
scalar score. Negation is exactly the distinction that compression is worst at, and
nothing in a cross-entropy loss on argmax labels rewards noticing it.

WHAT TO DO:

1. **Test negation explicitly, before you ship.** Take your rules and write each one
     both ways -- "eligible if X" and "ineligible if X" -- and check the model
     inverts correctly. A dozen such pairs will find this in an afternoon.
2. **Prefer option sets that are mutually exclusive and exhaustive.** If every option
     is genuinely a distinct case, there is less room for a negation to be missed
     than if one option is "none of the above" and another is a long negative
     description.
3. **Watch the ordinal kernel here.** Our `score` target puts 20% of its mass on
     adjacent levels, which is right for "how urgent" and wrong for "is this
     excluded". Ordinal hedging and negation confusion are different failures; do not
     let a fix for one mask the other.

11.11 AND A WARNING ABOUT YOUR OWN ADVICE
------------------------------------------
From the same changelog, and it is worth internalising precisely because this guide
recommends thresholding:

    "**Read the calibration rows before you upgrade.** 1.1 gave up half the sharpness
     1.0 had on `sim_local_ood`... **If you threshold `confidence` rather than read
     the argmax -- which this README spends a section recommending -- that is the one
     axis where the newest checkpoint is not the best one.**"

The newest model is the best on accuracy and the *worst* on the axis you would use for
routing. Their `sim_local_ood` qL2: 1.0 **0.0096**, 1.1 0.0203, 1.2 0.0161.

So: **re-fit and re-measure calibration on every checkpoint you consider, including
ones you believe are upgrades.** "Newer" is not a calibration argument. This is the
same lesson as refitting temperature per quantisation format, and as the MLX card
whose held-out ECE got *worse* after its own temperature fit.

The other thing that changelog teaches is a training-data shape you can copy. The 1.1
release added 64,028 composed-decision questions over 112 rule structures and 40
domains, plus **two loss terms that only a generator can produce**:

  - the same decision rendered four different ways, which must be answered the same
  - two different policies over one state, which must NOT be answered the same

That second one is a direct counterexample to the "composed decisions" task, and it is
the kind of negative pair that teaches a readout to actually use the policy rather
than pattern-match the state.

12.3 A DECISION POLICY, WRITTEN OUT -- AND MEASURED
---------------------------------------------------------
Most guides stop at "pick a threshold". We ran the model, so here is what its
curve actually says. From our saved per-question outcomes, n=300 eval
questions, LoRA arm, exact Clopper-Pearson intervals:

    coverage   accuracy   95% CI          frozen arm, same eval
        2%       1.000   [0.607, 1.000]      0.667
        5%       1.000   [0.819, 1.000]      0.600
       10%       0.933   [0.805, 0.988]      0.500
       20%       0.817   [0.715, 0.894]      0.467
       30%       0.811   [0.730, 0.876]      0.389
      100%       0.563   [0.514, 0.611]      0.323

    automatable coverage at an error budget:
      <= 2%  ->   8.0%      <= 5%  ->   9.7%      <= 10% ->  11.0%
      <=20%  ->  33.7%      <=30%  ->  50.0%

The frozen arm has **coverage 0.0% at every budget from 2% to 30%**. Its single
highest-confidence prediction was WRONG. There is no threshold that makes it
usable, which is a stronger statement than "it scores worse".

SO WRITE THREE BANDS, not one threshold:

    top ~8-10% of decisions    accuracy 0.93-1.00  -> act automatically
    next ~20-25%               accuracy 0.81-0.93  -> act, log, sample for audit
    bottom ~70%                accuracy ~0.50      -> escalate to a person
                                                    or a bigger model

**DO NOT PROMISE "100% ACCURATE".** The 5%-coverage point is 15 questions with
zero observed errors; the 95% lower bound is 0.819. The honest phrasing is "no
errors observed in 15", and any threshold set from it is optimistic. Quote the
interval, not the point estimate.

**THESE BANDS ARE NOT A RECOMMENDATION FOR YOUR DATA.** They come from one
workflow, 360 training questions and 3 CPU epochs. A model trained on 10k
examples moves every row. Re-run `python experiments/risk_coverage.py <run.json>`
against your own held-out set and set thresholds from *that* curve.


-----------------------------------
The probabilities are for routing. Say so in your docs and your UI.

    p_max = max(answer.probabilities.values())

    if p_max >= 0.90:  act_automatically(answer)
    elif p_max >= 0.60: queue_for_review(answer)      # sample these, they're
                                                       # where the errors live
    else:               escalate_to_a_person_or_a_bigger_model(answer)

Pick those thresholds from a measured accuracy-at-coverage curve on YOUR data, not
from these numbers. Kev's observation is the right way to think about the middle
band: at a 5% error budget, Kev can automate 0.45-0.57 of decisions and Jev 0.70.
The automatable share is a property of your threshold AND your data.

PART 13 -- WHAT THE DEPLOYMENT EVIDENCE CHANGED
================================================================================

Everything in Parts 0-12 came from artefacts: model cards, config files,
papers, source code. This part is different. It comes from what happened when
people actually RAN the things, and it changes three of this guide's
conclusions.

13.1 THE BAR IS 0.766, AND SOMEONE ALREADY CLEARED IT
----------------------------------------------------
`typed-decisions` is 2,000 decisions across four workflows -- the same data we
score on. Open weights, Apache-2.0, at our size class:

    laya-typed-decisions (421M)               0.766
    base laya zero-shot (421M)                0.362
    our LoRA arm (354M, 360 train questions)  0.5633
    our frozen arm (354M)                     0.3233

Trained by a different person, on ONE RTX 6000 Pro (96 GB), on a fully
human-annotated corpus. We are ~20 points below, on CPU, with 360 questions
and 3 epochs.

OUR FINDINGS ARE ABOUT METHOD, and none of them need to be SOTA to be true.
But be clear-eyed about where you start. If your goal is a working component,
**steal the weights.** If your goal is to learn the method, you have a 20-point
gap to close, and that is a good project.

13.2 CALIBRATION IS THE THING TO OPTIMISE, NOT ACCURACY
-------------------------------------------------------
This is the most useful thing the deployment layer produced, because it
independently confirms our own weirdest result.

kyr0, on Laya -- the fastest model in the field, at 36.7 ms:

    "it's fast but only performs well on a non-diverse benchmark, and
     CALIBRATION IS REALLY BAD"

and his own 76%-accurate model sits at ECE-15 of 13% against Jev's 8.4%. So
the MORE accurate model is the BETTER calibrated one, and the small fast one
is the badly calibrated one.

That is our frozen-arm finding (T 3.300, coverage 0.0000 at a 5% budget)
arriving from the opposite direction, on hardware we do not have.

PRACTICAL CONSEQUENCE: a badly calibrated decision model has NO USABLE OPERATING
POINT. You cannot threshold it. It is worse to ship than a less accurate but
well-calibrated model, because an inaccurate-but-honest model tells you when to
escalate and a dishonest one does not. Optimise calibration first, accuracy
second. Argmax is nearly free and almost never the thing that is broken.

13.3 DO NOT TRUST ANY LATENCY NUMBER IN THIS FIELD
--------------------------------------------------
Four independent measurements of Jev-class latency:

    Jev-Omni's own card         83 ms    in-process, H200, 1 question
    awesome-jev-projects radar  50-100 ms  UNSTATED shape
    Ollaya                    236-276 ms  hosted, 5 questions
    typed-decision-bench       716 ms p50 H200, includes HTTP

A 14x spread. The request shapes differ so much that these may not be the same
operation. Every source agrees on the DIRECTION -- local small-model decisions
beat a hosted round trip. Nobody agrees on the multiple.

The largest census of the field says why. Of 693 catalogued projects:

    376 (54%)  "performance and cost benefits have not been independently
                verified"
    352 (51%)  "consult the source for the exact decision policy" -- i.e. the
               reviewer could not confirm what decision the project makes

Only 2 of 693 projects are filed under Classification. 56% of the field is
orchestration, routing, MCP, guardrails, context GC and evaluation. A field
whose pitch is "a small model that classifies" is building plumbing around
classifiers, not classifiers.

PRACTICAL CONSEQUENCE: when you benchmark, publish the REQUEST SHAPE or the
number is worthless. Measure one question and five. Say whether the network is
in it. The awesome-jev-projects provenance block is a good template: it states
WHERE the decision happens and what the project actually offers. Copy that
discipline into your own repo.

13.4 THE HONEST FAILURE, AND WHY IT IS THE MOST USEFUL THREAD
-------------------------------------------------------------
Someone ran Jev against real markets for 24 hours and posted the result:

    731 trades, -3.15% (-$3,150), ~$1,650 of it fees
    21% of trades profitable after fees
    779 ms average per decision

The setup was FAIR to the model. Twelve indicators. Candle history. And the
costs handed to it EXPLICITLY -- commission, exchange fees, slippage,
round-trip ticks -- with the question posed directly as whether a move was
likely to clear them. Entry required >50% probability. A hard $500 stop was
imposed OUTSIDE the model. It churned anyway.

The author's own summary is the lesson:

    "So far, it's very efficient at generating commissions."

The question they could not answer in 24 hours is YOUR question:

    "whether higher probabilities actually lead to better trades after costs"

That is the coverage@5% problem, asked in production instead of on a held-out
split. And the paired anecdote reached the OPPOSITE conclusion the same week, so
neither one is evidence -- which is exactly why every measurement in this guide
is labelled with its seed.

PRACTICAL CONSEQUENCE: do not ship a decision model into a loop that can act.
The 287-project survey's own summary of how this is used correctly is the
design brief:

    big model -> Jev -> code -> Jev -> tool -> Jev -> big model

Jev chooses, filters, routes, gates, and judges whether an agent's completion
claim is supported. Code executes. json-render does not let Jev build the UI.
The trading bot does not let Jev place orders unguarded. The drone project keeps
classical control for flight stability and puts Jev one level up.

13.5 TWO SMALL THINGS WORTH STEALING
-------------------------------------
1. Laya ships with a 1,024-token default that SILENTLY TRUNCATES long
   documents, and says so in bold. Make your context handling as loud about it.
   A decision model that quietly reads half your state is worse than one that
   refuses.

2. Ollaya and Bonsai-Llama-Jev both implement TypeSafe's /v1/systemone so the
   OFFICIAL TypeSafe SDKs run unchanged against a local engine. If your
   deployment survives the model being replaced, the port is cheap; if it does
   not, every model swap is a rewrite. Make the INTERFACE the artefact.
